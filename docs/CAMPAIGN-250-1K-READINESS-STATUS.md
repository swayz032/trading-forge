## Known tooling facts
- `tsc` needs `NODE_OPTIONS=--max-old-space-size=8192` (default heap OOMs SIGABRT 134 — NOT a type error).
- `system-map:check` is DRIFTED at baseline (pre-existing "Generated topology stale" + n8n health staleness = audit H-11) — waves verify "no NEW drift", don't attribute it.
- Housekeeping: leftover `wt-f3-bartime` dir (Windows file-lock on removal; git deregistered it) — prune later.
- **`git worktree remove --force` can wipe the shared target `node_modules` mid-command when the worktree's `node_modules` link isn't cleanly unlinked FIRST, as a separate sequential step** (M2 grading session + W3A cleanup, both 2026-07-17) — same underlying hazard as the known junction-`rm -rf` class, but triggered by a git built-in, not a raw shell command. **"Prefer symlinks over junctions" does NOT work as a mitigation** — W3A's `node_modules` was created via the identical `ln -s` command M2's was, yet `rm node_modules` failed with `"Is a directory"` (the junction signature) and the subsequent `git worktree remove --force`, run in the SAME parallel batch as the failed unlink attempt, wiped `.bin/`, `drizzle-orm`, and most of `@types` from the shared tree. Fixed both times with `npm install`. **Actual safe procedure:** test `rm <path>/node_modules` (no `-r`) in isolation first — clean success means true symlink, safe; `"Is a directory"` means treat it as a junction (`cmd //c rmdir` instead) — and NEVER run the unlink step and `git worktree remove --force` in the same tool-call batch; sequence them with a confirmed-successful unlink as a hard gate. Always positively verify (`ls node_modules/.bin/tsc` exists) after ANY worktree teardown — a clean-looking exit 0 from `git worktree remove --force` is not evidence of safety. Full detail: `reference_rm_rf_junction_deletes_target_2026_07_09` memory.
- **A hardcoded "copy" of a real constant inside a test, even with a documented import-side-effect justification, is a fabricated-safety-claim risk — verify the obstacle is real before accepting the copy (M3, 2026-07-17).** `paper-authority-states.test.ts` hand-copied `server-mediated-executor.ts`'s `LIVE_EXECUTION_STATES` value because that file "transitively imports db/index.ts, which throws without DATABASE_URL" — but the actual obstacle was ONE import (`db/index.js`), not the whole dependency tree; a single `vi.mock("../../db/index.js", () => ({ db: {} }))` let the real module load cleanly. The independent grader RED-proofed the hand-copy version by widening the real constant and finding zero test failures anywhere — a live-capital-boundary safety claim that was silently false. Always probe the actual import obstacle directly (a throwaway dynamic-import test) before accepting a "can't test the real thing" test-design compromise.
- **A DB mock whose `.where()` ignores its filter argument is vacuous for any RED-proof that needs to distinguish "query correctly found nothing" from "the mock never looked at the condition anyway" (M3, 2026-07-17).** The `gate3-manual-precondition-wiring.test.ts` table-routing mock pattern (ignore-the-WHERE-clause, route by table identity only) is fine for asserting POSITIVE behavior, but a negative-case test built on it (e.g. "does NOT call X when the session belongs to a different strategy") would pass for the wrong reason — the mock returns the seeded row regardless of the real query's filter. Fix: mock `drizzle-orm`'s `eq`/`and` to return inspectable condition objects `{__op, col, val}`, then have the mock's `.where()` handler compare `col` by REAL OBJECT REFERENCE against the actual imported column (`paperSessions.status`, not a string name guess) — this makes the mock genuinely filter-aware and lets a RED-proof (e.g. typo'ing a status-literal in production) actually flip the test.
