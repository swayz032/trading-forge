# Slumhouse Kitchen — Menu, Premium Naming & Strategy Progress Line

**Date:** 2026-07-03
**Status:** Approved design — ready for implementation plan
**Surface:** Slumhouse PWA (`public/slumhouse/`, no build step) + backend `src/server/routes/slumhouse/` + `src/server/lib/slumhouse/`

## Goal

Turn the Slumhouse Kitchen from a single deployed-only "Today's Menu" into a full, premium strategy library: a **menu with category pages**, **premium human names** for strategies, **variant families** (same archetype at different timeframes/symbols/sessions grouped and raced), and a **premium animated 3D progress line** that shows any strategy passing/failing the validation gates. Plus a **banner swap**. All in the existing black-glass Slumhouse aesthetic. Nothing changes about the gates, lifecycle, or what decides promotion — this is presentation + naming only.

## Non-goals

- No change to gate logic, lifecycle transitions, or promotion decisions.
- No LLM-generated names (deterministic, operator-curated).
- No touching the deprecated amber-vision SPA library (Slumhouse is the real frontend).
- No new trading behavior.

## Component 1 — Premium naming

**Problem:** strategies carry raw canonical names (`orb_15m`, `ict_silver_bullet_ny_am`, `connors_rsi2`) generated by `prettifyConcept` in `direct-bucket-graduator.ts`. Not menu-grade.

**Design:** a premium name attaches to the **family** (archetype/concept), not the individual strategy row.

- **Curated map**, operator-owned: `familyKey → premiumName`. Lives in a new module `src/server/lib/slumhouse/premium-names.ts` as a plain exported constant object (code-level, versioned, easy to edit). Examples:
  - `opening_range_breakout` / `orb` → "Opening Heist"
  - `silver_bullet` → "Silver Bullet"
  - `connors_rsi2` → "The Dip Snatch"
  - `ema_9_21_pullback` → "Trend Rider"
  - `vwap_fade` → "The Fade"
  - `liquidity_sweep_reversal` → "Crude Sweep"
- **Resolution function** `resolvePremiumName(strategy) → { family, premiumName, variantTag }`:
  - `familyKey` = archetype from `config.entry_indicator` (strip `archetype:` prefix) OR the concept fingerprint base, normalized (lowercased, timeframe/symbol/session suffixes stripped).
  - `premiumName` = map[familyKey] if present, else Title-Cased prettified raw name (never blank).
  - `variantTag` = `${timeframe} · ${symbols[0]} · ${session?}` (session derived from the raw name / archetype when present, e.g. `ny_am`).
- **Fallback is mandatory** — every strategy resolves to *some* premium name so the menu is never blank.

**Interface:** `resolvePremiumName(row)` is pure given a strategy row; unit-testable with fixtures. No DB writes, no migration — names are derived at read time in the menu/recipe assemblers.

## Component 2 — Variant families ("cook-off + champion")

Same archetype at different timeframe/symbol/session = **variants of one family**.

- **Family key** = the normalized archetype/concept from Component 1.
- **Grouping** happens in the backend menu assembler: strategies are grouped by `familyKey`; each group is a family with N variants.
- **Champion** = the variant of a family furthest along the lifecycle, tie-broken by forge score / deflated Sharpe. Computed per family.
- **Menu behavior by page (Component 3):**
  - *Now Serving / Deploy-Ready* → show the **champion only** per family (one "Opening Heist"), with a small "N cuts tested" hint.
  - *In the Kitchen* → show the **family as a cook-off**: variants listed together, each with its own progress line, best cut highlighted.
  - *Graveyard* → tossed variants grouped under their family.

**Interface:** `groupIntoFamilies(rows) → Family[]` where `Family = { familyKey, premiumName, variants: VariantSummary[], champion: VariantSummary }`. Pure, testable.

## Component 3 — Menu category pages

Today: `assembleTodaysMenu()` returns DEPLOYED/DECLINING only, rendered on `kitchen.html`. Expand into four categories, each its own view/tab.

- **Backend** — new route(s) under `src/server/routes/slumhouse/api/`, backed by new assemblers in `kitchen-data.ts` (or a new `menu-data.ts`), all `requireSlumhouseUser`:
  - `GET /slumhouse/api/menu/now-serving` → deployed champions (reuse/extend `assembleTodaysMenu`).
  - `GET /slumhouse/api/menu/deploy-ready` → `lifecycle_state = 'DEPLOY_READY'` champions.
  - `GET /slumhouse/api/menu/kitchen?symbol=MES|MNQ|MCL` → testing families (CANDIDATE…PAPER) grouped, filtered by symbol, with per-variant stage/gate summary.
  - `GET /slumhouse/api/menu/graveyard` → GRAVEYARD strategies grouped by family with kill reason.
  - Each dish/variant row carries: `id`, `premiumName`, `variantTag`, `familyKey`, `symbol`, `lifecycleState`, key stats (avg R, win%, WFE / deflated Sharpe as available), and for kitchen rows a compact `gates[]` array (see Component 4) for the mini progress line.
- **Frontend** — a menu surface in Slumhouse. Decision: **tabs on a dedicated menu view** reachable from the Kitchen (keeps the Kitchen hero + pipeline; the menu becomes its own tabbed section/page). Tabs: `Now Serving · Deploy-Ready · In the Kitchen (MES·MNQ·MCL sub-pills) · Graveyard`. Each dish links to / opens the Recipe page (progress line). Rendered as `public/slumhouse/menu.html` (or an expanded section of `kitchen.html`), plain JS + `fetchJSON`, matching the black-glass card style.
- **Empty/stale/error states** honest (reuse the deep-scan #12/#13 patterns: real error, not "empty").

## Component 4 — Strategy progress line (the v6 design)

The locked visual: matte-black premium beads in machined bezels on a lit conduit, inside a floating black-glass card. States: cleared (lime ring) / cooking now (amber + halo) / failed (red) / not-yet (gunmetal). Animated (flowing conduit sheen, floating beads, spinning halo on the active gate). Gate labels are plain-English:

| Gate label | Sub | Backing check |
|---|---|---|
| Profitable | made money in testing | backtest completed, positive expectancy |
| Holds Up | works on unseen data | Walk-Forward (WFE ≥ floor) |
| Real Edge | not just luck | Frankenstein / A4 |
| Crash-Proof | survives a bad day | Black Swan / A14 |
| Paper Trial | fake money | PAPER stage, N days |
| Live Match | live = the test | Shadow divergence < threshold |
| Rule-Safe | won't break firm rules | compliance enforce |
| Live Money | on the menu | DEPLOYED |

- **Data:** a pure resolver `resolveGateJourney(strategy, recipeData) → Gate[]` where each `Gate = { key, label, sub, status: "pass"|"now"|"fail"|"wait" }`. Derives status from the strategy's lifecycle stage + the recipe "8 tests" (`recipe-data.ts` already computes these pass/warn/fail signals) + which gate is currently active (the lifecycle frontier) + the kill reason (which gate failed for graveyard). Reuses `recipe-data.ts` gate signals — no new gate computation.
- **Where it lives:**
  - **Recipe page** (`recipe.html`) — full progress line for that strategy (replaces/augments the current "8 tests" list rendering with the animated line; keep the honest status logic from deep-scan #13).
  - **Menu** — tapping a dish opens its Recipe page (which shows the line). In the Kitchen cook-off, each variant shows a **compact** version of the line inline.
- **Component:** a shared, reusable renderer `public/slumhouse/progress-line.js` (a function that takes a `Gate[]` + a container and draws the card+line), used by both recipe.html and the kitchen cook-off. Pure DOM, no framework. CSS from v6 lives in a shared block (inline in the component or a `.css` partial).

## Data flow

```
strategies (DB) ─┬─ assembleKitchenData()  → 6-stage counts (unchanged)
                 ├─ menu assemblers (new)  → groupIntoFamilies() → resolvePremiumName()
                 │        → /slumhouse/api/menu/{now-serving,deploy-ready,kitchen,graveyard}
                 └─ recipe assembler       → resolveGateJourney() → Gate[]
                                            → recipe.html + progress-line.js
```

## Testing

- Unit (vitest, `src/server/__tests__/slumhouse/`): `resolvePremiumName` (mapped, fallback, variant tag), `groupIntoFamilies` (grouping + champion selection + tie-break), `resolveGateJourney` (pass/now/fail/wait derivation incl. a killed strategy), each new menu assembler (shape + category filtering).
- Route tests: each new `/slumhouse/api/menu/*` route requires session + returns the right category.
- Honest-state tests (carry the deep-scan #13 discipline): backend-down / empty / missing-gate render as real states, never fabricated.
- No engine/DB-integration tests needed (pure resolvers + read assemblers).

## Phasing (suggested build order)

1. **Naming + families** (pure libs `premium-names.ts`, `resolvePremiumName`, `groupIntoFamilies`) + tests. Foundation for everything.
2. **Progress line component** (`resolveGateJourney` + `progress-line.js` + v6 CSS) wired into `recipe.html`.
3. **Menu category pages** (new assemblers + routes + `menu.html` tabbed frontend, dishes open recipe).
4. **Kitchen cook-off** (family variants racing, compact line inline).
5. **Banner swap** (trivial; can land anytime).

Each phase is independently shippable and testable.
