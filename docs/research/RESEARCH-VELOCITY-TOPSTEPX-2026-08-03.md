## Executive summary

The single highest-leverage acceleration found this pass: **stop hand-qualifying a growing battery of bespoke checkers, and instead build one deliberately simple, obviously-correct reference interpreter for the compiled strategy's intermediate representation, then make differential testing between that reference interpreter and the real compiled path the primary oracle.** This is not novel — it is the dominant 2025-2026 architecture for exactly this class of problem (JIT-compiler correctness testing, LLM-code-translation validation, and — concretely, in the trading-DSL domain itself — a third-party's 245/246-strategy, 375,000-trade differential-parity corpus built against TradingView's real Pine compiler, §1.2). The qualification burden moves from "N bespoke checks, each needing its own qualification" to "one reference implementation plus an off-the-shelf differential harness," which is qualitatively cheaper to establish and to re-qualify after every compiler change — directly addressing "verification regress." Part 2 gives the supporting discipline for whatever bespoke checking still remains on top of that. Part 3 gives concrete, shipped, disclosed-architecture examples of how other teams operationalize LLM-codegen-plus-verification loops end to end, including one directly in the trading-strategy-codegen domain.

**Why this is the "avoid bespoke checker-qualification regress" answer:** every bespoke checker Trading Forge writes (a hand-authored assertion, a specific unit test for a specific rule) itself needs qualification — evidence that the checker correctly discriminates good from bad — which is exactly the mutation-testing-style regress the operator is trying to escape (Part 2). A reference interpreter has a fundamentally different qualification burden: it needs to be shown faithful to the frozen spec semantics **once**, as a whole — and it can be deliberately slow/unoptimized/structurally simple precisely *because* independence from the thing-under-test is what gives it oracle power (the classical differential-testing insight, evidenced above and demonstrated in the wild by PineForge). After that one-time qualification, every subsequent compiler change is checked by running both paths and diffing — no new checker to qualify per change, no growing battery to maintain.

### 1.3 Trading-specific benchmarks — the strongest, most directly relevant finding this pass *(carried forward unchanged)*

Two purpose-built 2026 academic benchmarks exist for exactly this problem (strategy-description → executable trading code, verified). Both were fetched and read in full, not just titled:

**SysTradeBench** (Cao, Zhang, Keung, Chen, Song; arXiv 2604.04812; **research tier; published 2026-04-06**):
- Treats LLM-generated trading systems as "governed, auditable software," not one-shot profitability generators.
- Requires three deliverables per submission: (i) a **strategy card** (structured interpretation of the spec), (ii) executable code, (iii) **mandatory audit logs** tracing signal → risk_check → order → position → P&L.
- A sandboxed harness runs **determinism checks**, **anti-leakage checks**, detects **rule drift across iterations**, and returns evidence bundles supporting only *constrained* patches (preventing a model from silently "fixing" a test by changing the strategy's semantics instead of the bug).
- Scores four dimensions: **D1 Spec Fidelity, D2 Risk Discipline, D3 Reliability, D4 OOS Robustness Indicators**.
- Evaluated 17 models × 12 strategies: top models reach ≥91.7% validity with 7.29–7.85/10 composite scores.
- **Critical, load-bearing finding for any iterative compiler-repair loop:** "evidence-driven iteration induces code convergence (95.4% similarity by Iter2)" — i.e., patch-and-retest loops cause generated solutions to homogenize rapidly. The paper's explicit conclusion: **"LLM iteration complements rather than replaces human Quantitative Researcher (QR) governance: LLMs excel at rapid prototyping and shallow bug fixes, while QR oversight remains essential for critical strategies requiring solution diversity and ensemble robustness."**
- Positions itself against four sibling 2025-2026 benchmarks (Market-Bench, QuantEval, StockBench/LiveTradeBench, PredictionMarketBench), confirming this is a genuine, multi-team, active research cluster — not one isolated paper.

**QuantCode-Bench** (Khoroshilov, Chernysh, Ekhtibarov, Kamkia, Zmitrovich; arXiv 2604.15151; **research tier; published 2026-04-16**):
- 400 tasks, Backtrader framework, sourced from Reddit/TradingView/StackExchange/GitHub/synthetic descriptions.
- **Four-stage pipeline**, explicitly nested: (1) syntactic correctness, (2) successful backtest execution, (3) presence of at least one actual trade, (4) semantic alignment via an LLM-judge comparing behavior to the natural-language spec.
- Its central, quotable claim: **"the main limitations of current models are not related to syntax, but rather to the correct operationalization of trading logic, proper API usage, and adherence to task semantics."** Compiling and running is explicitly called out as *insufficient* evidence of correctness.
- Single-turn (no feedback) vs. agentic multi-turn (iterative repair with feedback) comparison: the abstract states single-turn best-model Judge Pass is **70–76%**, rising to **95–98%** with agentic iteration; note the paper's own introduction text separately states single-turn "does not exceed roughly half of the benchmark" — **this is an internal inconsistency in the source itself**, reported transparently rather than silently resolved in one direction. Whichever exact number is correct, the qualitative finding is robust across both statements of it: iterative, feedback-driven repair produces a very large fidelity improvement over one-shot generation.

**Triangulation verdict:** 2 independent, full-text-read, 2026-dated, research-tier benchmarks converge on the same architecture (multi-stage: syntax → execution → behavioral/trade-presence → semantic judge/spec-fidelity, with iteration monitored for drift/diversity loss) — a strong, non-single-source answer to how spec-fidelity should be measured.

### 1.7 What teams measure vs. what they skip — consolidated answer *(carried forward unchanged)*

**Measured, per the 2025-2026 evidence above:**
- Syntactic/compile correctness (necessary but explicitly called out as insufficient by both trading-specific benchmarks).
- Execution success + presence of actual observable behavior (QuantCode-Bench's "does it actually place trades" stage — directly analogous to "does the compiled strategy actually generate the signals the spec describes," not just "does it run without crashing").
- Semantic/behavioral alignment to the original spec, via an independent judge (LLM-as-judge in QuantCode-Bench; frozen machine-checkable semantics + strategy-card cross-check in SysTradeBench) — never via text-similarity metrics alone (Beyond BLEU, 2026-05-06).
- Determinism and anti-leakage (SysTradeBench) — i.e., does the same input reliably reproduce the same trace, and does the strategy avoid using information not yet available at decision time.
- Audit-log completeness (SysTradeBench's mandatory signal→risk_check→order→position→P&L trace) — matching Trading Forge's own audit-trail-complete mandate.
- Solution diversity / convergence risk across iterative repair passes (SysTradeBench's 95.4%-similarity-by-Iter2 finding) — an explicit, measured red flag for over-iterating against the same test feedback.

**Skipped or explicitly flagged as insufficient when used alone:**
- Compilation/execution success alone (both trading benchmarks explicitly show this is where naive evaluation stops and where the real failures live).
- Text-similarity-based translation scoring (BLEU/CodeBLEU) — shown unrelated to semantic correctness.
- Self-generated test suites without an independent oracle — the "AI writes the flaw and the test that validates the flaw" failure mode (HackerNoon, undated-2026-indexed).
- A single "iteration until tests pass" loop without a diversity/convergence check — SysTradeBench's paper treats unmonitored convergence as a governance gap requiring human QR oversight, not something solved by more iteration.

### 1.8 Scale translation for Trading Forge

- **Reference interpreter + differential testing as the primary oracle: required at our scale — the single highest-leverage recommendation in this report.** Cheaper to build and re-qualify than a growing battery of bespoke checks; directly evidenced as working at high fidelity in the trading-DSL domain itself (PineForge's 245/246 result, §1.2); qualification burden is "prove one reference interpreter faithful to the frozen spec, once" rather than "qualify N checkers forever."
- Golden-trace/property-based tests for structural invariants (fee monotonicity, cash invariance, conservation-of-volume-style checks, OHLC/timestamp sanity, §1.5): **required at our scale** — cheap, reusable across every strategy (unlike bespoke per-strategy checks), each pattern a few lines of Hypothesis-style code, and 3 independent ≥2025 sources converge on this as standard practice.
- Requiring a structured intermediate representation ("strategy card") that the reference interpreter executes, cross-checked against frozen spec semantics: **required at our scale** (§1.3/SysTradeBench, directly synergistic with the reference-interpreter architecture above — the intermediate representation IS what the reference interpreter runs).
- Treating "compiles and produces a good-looking trade list" as sufficient: **explicitly evidenced as insufficient** — both trading-specific benchmarks (§1.3) and the Pine practitioner account (§1.6) show clean compilation can still hide wrong execution-model semantics.
- Literal replication of a full academic multi-model benchmark harness (SysTradeBench/QuantCode-Bench's own 12-17-model comparisons): **over-engineered** — their evaluation *dimensions* are adoptable as a checklist at near-zero cost; their comparison methodology is not something to rebuild.
- A full Antithesis-style deterministic-simulation-testing layer on top of everything else: **over-engineered at our scale today** — even Jane Street frames it as a gap-filler *after* an already-mature quickcheck/fuzz/chaos/unit/integration stack, not a starting point (see §2.7).

### 2.3 Test-oracle qualification methodology

The search surfaced a genuinely thin, scattered literature rather than one canonical methodology — reported honestly rather than forced into false coherence:

- General software-testing sources (testRigor, 2025-12-30; Wikipedia's Test Oracle entry, background/definitional only) reiterate the standard framing: an oracle provides ground truth to judge SUT output, and human oracles don't scale.
- A 2026 practitioner piece, "Test Oracles You Can Trust in 2026: From Spec Math to Safe Automated Verdicts" (TheLinuxCode, 2026-02-15, blog-general), frames oracle trust as a function of how directly the oracle traces back to a formal spec ("spec math") vs. a learned/approximate proxy.
- The most rigorous ≥2025 items found concern oracle qualification for **agentic/LLM systems specifically** rather than classical software: "Verification Without Ground Truth: How Oracle Weakness, Post-Hoc Selection Failure, Behavioral Fingerprinting, and Structural Monitoring Jointly Expose a Candidate Framework for Agent Output Trustworthiness" (research, 2026-06-18) and "Oracle-Gated Agent Loops: Certifying-Algorithm Discipline for AI-Assisted Development of Safety-Critical Software" (PulseEngine preprint, 2026-07-16) both argue that a single oracle channel is insufficient for agent-generated artifacts and argue for **multiple, structurally-independent verification channels** (a theme that directly supports triangulated, multi-channel qualification over single-pass "did the check come back clean" reasoning).
- **Verdict: INSUFFICIENT EVIDENCE for a single named "test-oracle qualification methodology" that is industry-standard in 2025-2026.** What exists instead is a consistent *directional* consensus across ≥3 independent 2026 sources (TheLinuxCode, the agent-output-trustworthiness paper, Oracle-Gated Agent Loops) that oracle trust should be built from **multiple independent, structurally-different verification signals**, not one. This directional finding is corroborated and is used below in the stopping-criteria discussion; a fully codified "qualification methodology" as a named framework was not found and is not invented here.

### 2.4 Stopping criteria — the operator's actual question

**Is "stop when adversarial passes come back empty" a valid, sufficient criterion?**

**Evaluated verdict: valid as a NECESSARY signal, INSUFFICIENT as a SUFFICIENT one, on convergent 2025-2026 evidence from 4 independent sources (now 5, with §2.7's Jane Street corroboration).**

1. **Equivalent mutants create an irreducible non-zero floor**, meaning "zero survivors" is not even a coherent target: "An equivalent mutant is a mutation that produces source code with different syntax but identical observable behavior, so no test can ever kill it" (CircleCI engineering blog, "What is mutation testing?", blog-general — cited via search snippet, date not independently confirmed ≥2025 in this pass; treated as corroborating color, not load-bearing). The **load-bearing, dated version of this same point** comes from Trail of Bits (corporate-eng, 2026-04-01, fetched in full): "Not all uncaught mutants matter. Mutations that change `x > 0` to `x != 0` are semantic no-ops when `x` is an unsigned integer... A perfect mutator wouldn't generate such mutations in the first place." **Implication:** a raw "adversarial pass came back empty" reading conflates "nothing new found" with "fully qualified" — you need a normalized score against a known non-zero floor, not a raw pass/fail.
2. **An empty result can mean the generator exhausted its own narrow bag of tricks, not that the target is safe.** Trail of Bits again: "without mutant prioritization, the tool wastes time on redundant mutations. When commenting a line triggers no test failures, universalmutator still generates and tests every possible variation of that line, dramatically extending campaign runtime" — a narrow/redundant attack surface returning "empty" says nothing about untested operator classes.
3. **Diminishing-returns/saturation is the right lens, not a single binary pass.** MIST-RL (research, 2026-03) explicitly models and graphs saturation curves, showing effort against marginal fault-discovery rate — the correct 2026 signal is *the shape of the finding-rate curve crossing a low threshold*, not "the last run found nothing."
4. **Depth of verification should be risk-tiered, not uniform.** Multiple 2026 risk-based-testing sources (testingmind.com "A Practical Approach to Risk-Based Testing in 2026," 2026-01-19; totalshiftleft.ai risk-tier table, undated-but-2026-context) converge on scaling verification depth to a risk score (critical → full coverage + manual exploratory; low → minimal automated) rather than one flat exhaustion criterion applied everywhere.
5. **Counter-consideration, honestly reported:** for continuous, cheap E2E suites specifically, one 2026 source argues the simple "green + coverage in place" signal is defensible ("When E2E testing is continuous and cheap, the question shifts from 'did we test enough' to 'is the suite green?'" — bug0.com, 2026-05-13, blog-general). This is a real, dated counter-data-point, not suppressed here — but it explicitly conditions the simpler criterion on near-zero marginal cost per additional cycle, which does not describe an expensive verification pass (e.g., a full backtest/Monte-Carlo/shadow-trading cycle).

**Net verdict for Trading Forge's current gate:** "adversarial passes come back empty" should be **necessary but not sufficient**. On this evidence, it should be paired with (a) a normalized score against a known floor (Meta's ACH shows this is achievable with measured precision/recall for the floor-detection step itself: 0.95/0.96 with pre-processing), (b) explicit tracking of the marginal finding-rate curve across successive passes rather than a single last-pass read, and (c) a risk-tiered depth policy so cheap/low-blast-radius surfaces can stop earlier than expensive/high-blast-radius ones. Part 1's reference-interpreter architecture is itself the cheapest available way to shrink how much "adversarial pass" surface needs this treatment in the first place — see §1.2.

### 2.5 Cheaper alternatives (named, dated, evidenced)

1. **Severity/risk-tiered mutant prioritization** (Trail of Bits' slither-mutate/MuTON, 2026-04-01; Atlassian's AI-guided prioritization, 2026-04-20) — skip low-value mutants once higher-value ones on the same surface already prove a gap.
2. **Concern-scoped mutant generation** (Meta ACH, 2025) — generate mutants only for the specific fault class under review (e.g., a specific new instrument-check or gate), not exhaustively across the whole codebase.
3. **Two-phase campaigns** (Trail of Bits, 2026-04-01) — fast targeted subset first, full-suite retest only on what survives the fast pass.
4. **RL/ML-guided mutant selection tracking a saturation curve** (MIST-RL 2026-03; PRIMG 2025) — stop investing further effort once the marginal discovery rate crosses a pre-declared low threshold, rather than running to literal exhaustion.
5. **Automated equivalent-mutant triage** (Meta ACH's LLM classifier, precision 0.95/recall 0.96 with pre-processing) — removes the noise floor from the score so "still surviving" more reliably means "actually untested," making a smaller mutant budget more informative per unit.
6. **Replace the need for many bespoke checkers in the first place** (Part 1, §1.2) — a reference interpreter plus differential testing shrinks the surface that needs mutation-style adversarial qualification at all, since correctness is established structurally rather than assertion-by-assertion.

### 2.6 Scale translation for Trading Forge

- Severity/risk-tiered prioritization: **required at our scale** — the cheapest lever with the strongest, most consistent 2025-2026 corroboration (4+ independent named sources); low implementation cost relative to payoff.
- Concern-scoped generation (Meta-ACH-style): **beneficial at our scale** — directly maps to "re-qualify only the part of the compiler/verification surface that changed," which is exactly the single-operator iteration loop; full ACH-grade LLM equivalent-mutant classification with measured precision/recall is likely **over-engineered** to build from scratch, but the *concept* (don't let equivalent-mutant noise count against your "still empty" signal) is cheap to apply manually.
- Tracking a marginal finding-rate curve instead of a single binary "did this pass find anything": **required at our scale** — this is a bookkeeping change (log finding counts per verification pass over time), not an infrastructure build, and directly closes the gap this section identifies.
- A full academic-grade saturation-detection framework (formal submodularity-based stopping bounds): **over-engineered at our scale** — no evidence found this pass that this is standard even at the corporate-eng tier (Meta/Atlassian/Trail of Bits all describe pragmatic heuristics, not formal stopping proofs).

### 2.7 One further corroboration, and a named higher-fidelity layer beyond mutation/property testing (context, not a recommendation at this scale)

Jane Street's own account (§1.5) independently corroborates this Part's central verdict from a source this report had not yet used when Part 2 was first drafted: "adversarial passes come back empty" (in their case: quickcheck + fuzz + chaos testing all green) was necessary but demonstrably not sufficient — a real, month-old bug survived all of it until a higher-fidelity layer (Antithesis, deterministic simulation testing — running the whole system in a deterministic-hypervisor VM with injected scheduling/network chaos, "you don't need to change your system to use" it) caught it on its first run. Jane Street co-led Antithesis's $105M Series A specifically "to make deterministic simulation testing the new standard" (PR Newswire, corporate/wire tier, **2025-12-03**), and Antithesis is separately reported to have "validated Ethereum's Merge" (press coverage, 2025-12-05) — i.e., this is a real, adopted-elsewhere practice, not a Jane-Street-only curiosity, though this report only has one first-hand technical account (Jane Street's) of its efficacy, so it is named here as **context for what "beyond mutation/property testing" looks like at the frontier**, not folded into the triangulated recommendations above.

**Scale translation: over-engineered for Trading Forge today** — it targets whole-distributed-system nondeterminism (scheduling/networking races) that a single-operator, largely batch-oriented compiler-and-backtest pipeline does not have in the same form; revisit only if/when Trading Forge's runtime becomes a genuinely concurrent, multi-process live system where such races become possible.

### 3.4 The common architecture across independently-shipped examples

Four elements recur across the three most-detailed cases (Block, G-Research, CrossTrade) despite completely different domains (security scanning, code review, trading-strategy generation):

1. **An independent oracle the LLM cannot talk its way around** — G-Research's rules index validated via Pydantic (the model "can suggest, but never define"); CrossTrade's real compiler + real Strategy Analyzer engine (never the model's own claim about what the code does); Block's schema-constrained structured output that still requires downstream validation. This is the same principle as Part 1's reference-interpreter pattern, applied to the LLM-authorship step specifically rather than the compiler step.
2. **Two-stage recall-then-precision, not one pass.** G-Research explicitly splits "capture everything" from "filter false positives" into two separate LLM calls; Block splits open-ended discovery from targeted category-specific audit; CrossTrade's compile-then-backtest is a weaker version of the same idea (compile catches structural issues, backtest catches behavioral ones). This directly matches Part 2's stopping-criteria finding (§2.4) that a single pass/fail read is insufficient.
3. **Testing non-deterministic output structurally, not by exact match.** G-Research tests "rule ID, file, severity" while explicitly ignoring wording/ordering — the same design insight as differential/golden-trace testing (compare what must be invariant, not everything).
4. **An explicit, human-gated stop before anything irreversible.** CrossTrade states this most directly ("do not vibe deploy trading code" — deploy only after green compile + passing backtest + explicit user confirmation); G-Research "deliberately decided not to block merges... there is still a human involved."

### 3.5 Scale translation for Trading Forge

- An independent oracle the compiler's own output cannot satisfy by construction (the reference interpreter from Part 1, or a rules-index-style frozen-spec check): **required** — this is the load-bearing pattern across every shipped example found.
- Two-stage recall-then-precision verification instead of one pass: **required, cheap** — directly actionable as "run the adversarial/differential pass broadly first, then a second narrower pass to characterize/dedupe what it found," rather than treating one pass as the whole story (reinforces Part 2, §2.4).
- Structural (not exact-match) testing of any inherently non-deterministic LLM output (e.g., generated rationale/comments): **required where applicable, near-zero cost.**
- An explicit human-gated stop before any live-capital action: **required, already Trading Forge's stated posture** (operator holds the keys) — the shipped examples independently confirm this is not over-caution, it is what serious shipped LLM-verification loops actually do.
- Rebuilding a full 200-agent automated-PR pipeline (AgentField-style) from scratch: **over-engineered at our scale** — the pattern is worth knowing about; the infrastructure is not proportionate for a single-operator campaign.
