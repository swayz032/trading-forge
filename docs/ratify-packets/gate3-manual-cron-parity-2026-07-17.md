## 1. What & why

**Verified defect:** the PAPER → DEPLOY_READY promotion gate has TWO independent callers of the same underlying evaluator, and only ONE of them checks the actual qualification precondition.

- **Cron sweep** (`lifecycle-service.ts:5567-5601`, inside `checkAutoPromotions`): for every strategy in `PAPER` state, computes `tradingDays` (distinct calendar dates on which `paper_trades` closed via `paper_sessions` since `strategy.lifecycleChangedAt`) and `rollingSharpe` (`strategy.rollingSharpe30d`), and gates: `if (tradingDays >= 30 && rollingSharpe >= 1.5) { ...run the 9-gate evaluator stack... }`. Strategies that haven't accumulated 30 qualifying days or Sharpe ≥ 1.5 are simply never promoted by the cron.
- **Manual PATCH path** (`PATCH /api/strategies/:id/lifecycle` → `strategies.ts:711-756` → `lifecycleService.promoteStrategy()` → `LifecycleService._promoteStrategyInner()` at `lifecycle-service.ts:597`, PAPER→DEPLOY_READY branch starting `:663`): calls `evaluatePaperToDeployReadyGates()` (`paper-to-deploy-ready-gates.ts:370`) directly. That evaluator's OWN docstring (`:33`) states explicitly: *"The caller is responsible for: Checking the pre-conditions (tradingDays >= 30, rollingSharpe >= 1.5)"* — and the manual path's caller chain (route handler → `promoteStrategy` → `_promoteStrategyInner`) never performs this check anywhere. **Confirmed by direct read of all three files, not inferred from a docstring alone.**

**Consequence:** a correctly-HMAC-signed manual PATCH call (`ADMIN_PROMOTE_HMAC_SECRET`) can promote a strategy from PAPER straight to DEPLOY_READY with **zero trading days and Sharpe=0**, as long as the 9-gate evaluator stack (B14 twin, B14 ci_high, B15, WFE, parameter drift, DSR, Wave26 orchestrator, composite shadow, frozen-policy) happens to pass on stale/inherited backtest data. This is a manual/cron **gate-parity gap**, not a capital-at-risk incident today (DEPLOY_READY is one stage before PILOT, itself only a 1-micro canary; nothing in this campaign trades live capital) — but it means DEPLOY_READY can be reached without having earned it, which is exactly the class of promotion-gate integrity bug this campaign's Wiring-Verification Protocol exists to catch.

## 2. Blast radius

- Adds ONE precondition check to the manual PAPER→DEPLOY_READY promotion path. Does not touch the cron sweep's existing check (already correct), does not touch the 9-gate evaluator (`paper-to-deploy-ready-gates.ts`) itself, does not touch any other lifecycle transition.
- Fail-CLOSED: a strategy that doesn't meet the precondition is BLOCKED from promotion via this manual path (matches the cron's existing behavior — the cron simply never attempts promotion for such strategies; the manual path must now explicitly reject with a clear error rather than silently proceeding).
- No schema change, no migration. No change to `VALID_TRANSITIONS`, HMAC verification, or any other gate.
- Zero effect on any ALREADY-DEPLOY_READY/PILOT/DEPLOYED strategy (this only gates the PAPER→DEPLOY_READY transition attempt itself, not existing state).
- Superseded-not-wasted by M3: when M3 replaces the day-count+Sharpe precondition with the new 5-10-qualifying-day evaluator (consumed by both cron and manual per the plan), this fix's manual-side check will be swapped for a call into that shared evaluator — the parity principle (manual path enforces the SAME precondition the cron enforces) survives, only the precondition's substance changes.

## Plain-English for the operator

The system has two ways to promote a strategy from paper-testing to "deploy-ready" (the stage right before the tiny 1-micro live pilot): an automatic nightly check, and a manual button an admin can press. The automatic check correctly requires 30 days of paper trading and a good risk-adjusted return (Sharpe ≥ 1.5) before it will promote anything. The manual button forgot to require that — it only checked the other 9 quality gates, not "has this actually traded long enough to prove itself." Nothing live was ever at risk (deploy-ready still isn't live capital), but a manually-triggered promotion could reach that stage without having earned the 30 days. This fix makes the manual button enforce the exact same 30-day/Sharpe rule the automatic check already does.
