## Item 1 — Kill-switch trade-cap backstop (execution-time, Python-invoked)

**Verified current state (NOT the plan's claim — the plan named the wrong file/mechanism):** `getDailyTradeCapEnvDefault()` is never called in `paper-execution-service.ts` — it's only used in `paper-signal-service.ts`'s signal-time gate. The actual execution-time "belt-and-suspenders" kill-switch lives in `paper-execution-service.ts:1243-1659`, which invokes a Python `check_kill_switch` compliance-gate call. Within it:
- `:1279-1281` — `maxTradesPerSession = sessionCfg?.max_trades_per_day != null ? Number(...) : undefined` — NO env-default fallback.
- `:1303` — arming condition: `if (dailyLossLimit > 0 || (maxTradesPerSession !== undefined && maxTradesPerSession > 0))`.
- **The real gap:** when a session has NEITHER `daily_loss_limit` NOR `max_trades_per_day` set in its config (i.e., relying purely on the `TF_MAX_TRADES_PER_DAY` env default), the arming condition is false and the ENTIRE Python kill-switch call is skipped — not just trade-cap enforcement, but the daily-loss and consecutive-loss checks bundled into the same call too, for that invocation. This is a real belt-and-suspenders gap for env-default-only sessions.

**Fix — do NOT naively fall back to `getDailyTradeCapEnvDefault()` directly (this would introduce a NEW regression):** a naive fix (`maxTradesPerSession = sessionCfg?.max_trades_per_day != null ? Number(...) : getDailyTradeCapEnvDefault()`) breaks any session that ALSO has `daily_loss_limit` set: if `TF_MAX_TRADES_PER_DAY=0` (the documented debug-disable value), `maxTradesPerSession` becomes `0` (not `undefined`); the arming condition still fires (`dailyLossLimit > 0` is independently true); the payload at `:1346` does `maxTradesPerSession ?? null` — and `0 ?? null` evaluates to `0` (nullish coalescing does not intercept `0`) — so Python receives `0`, and `compliance_gate.py:667`'s `if max_trades_per_session is not None and trades_today >= max_trades_per_session` trips on the very FIRST trade of the day (`0 >= 0`). Today this can't happen because `undefined ?? null` → `null` → Python's `is not None` is `False` → correctly skipped.

**Correct design (mirrors the signal-time gate's own contract — reuse, don't reinvent):**
```ts
const effectiveCap = resolveEffectiveCap({
  perSessionCap: (sessionCfg?.max_trades_per_day as number | null | undefined) ?? null,
  envDefault: getDailyTradeCapEnvDefault(),
});
const maxTradesPerSession = effectiveCap > 0 ? effectiveCap : undefined;
```
`resolveEffectiveCap()` already exists and is exported from `daily-trade-cap.ts:89` (the exact same precedence — DB session override > env default — the signal-time gate already uses). Import it alongside the already-imported `getDailyTradeCapEnvDefault()` (note: `daily-trade-cap.ts` import line already exists in `paper-execution-service.ts`? — VERIFY at implementation time; if not, add it). This fixes BOTH: (a) env-default sessions now correctly arm the kill-switch, and (b) a dormant PRE-EXISTING bug where an explicit session-level `max_trades_per_day: 0` today ALSO tips through the same `?? null` gap and trips on trade #1 (nobody currently sets this value in practice, so it's dormant — but it's a real bug in the current code, fixed for free by the same one-line guard). Fix both in this same change — they're the identical class, not two separate defects.

**Preserve:** the `daily_loss_limit` path is completely independent and untouched (arms on its own, no change needed there). Do not alter the Python-side `compliance_gate.py:667` check itself — only the TS-side derivation that decides what value it receives.
