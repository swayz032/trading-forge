## 1. What & why
The internal paper engine — which under D6/D7 becomes the PAPER-stage promotion-evidence authority on the Massive delayed feed — is NON-deterministic and NON-durable in two ways external audits + the campaign plan flagged:
1. **`pendingEntryQueue` is an in-memory `Map`** (`paper-signal-service.ts:673`) holding deferred entries between a signal firing and its fill on the next bar. A process restart (NSSM respawn, tower reboot, deploy) BETWEEN signal and fill silently DROPS the pending entry — the trade never opens, and nothing records that it was lost. On the delayed feed / vacation-mode this is a real evidence hole.
2. **Fill simulation uses unseeded `Math.random()`** — latency-drift slippage (`:569`) and the fill-probability miss gate (`:1929`). Every draw was untraceable and irreproducible even from the position's own recorded identity → paper evidence could never be forensically reconstructed. This is the replay-determinism the campaign's own WIRED protocol demands.
   **Scope correction (accuracy-validator grade, 2026-07-17, F-3):** the property this wave actually delivers is *reconstructible-from-recorded-identity* determinism — given the same (sessionId, orderIntentId/correlationId, barTimestamp, fillModelVersion) tuple, the draw is byte-reproducible. It is NOT *fresh-tape* determinism: `paper-trading-stream.ts::processSessionBar` mints a new `correlationId = randomUUID()` per bar (H2, 2026-06-23, pre-existing, unrelated to M2, tape-content-independent), so replaying the identical OHLCV sequence from scratch in a fresh session still produces a fresh seed and therefore non-identical fills. "Same tape twice → identical fills" requires *also* reusing the recorded correlationIds from the first run — the RNG fix alone does not provide it. See `paper-trading-stream.ts:344` for the caveat comment.

## Plain-English for the operator
Two fixes so the paper engine's results are trustworthy evidence. (1) Right now, if the tower restarts in the split second between the bot deciding to enter a trade and actually filling it on the next bar, that trade silently vanishes — no record. This saves the pending entry to the database so a restart re-loads it and the trade still opens (exactly once). (2) The paper fills use random numbers, so running the same market data twice gives different results — you can't reproduce or trust a number. This seeds the randomness from the trade's own identity, so the same data always gives the same fills. Neither changes HOW slippage is calculated — only that it's now repeatable and crash-proof.
