## 0b. Bucket-anchor investigation (2026-07-17, read-only, pre-code — supersedes §3's original anchor suggestion)

**Finding: the consolidated parquet files bucket intraday timeframes (5m/15m/30m/1h/4h) on plain UTC-epoch boundaries — `group_by_dynamic`'s Polars default, i.e. `bucketStart = floor(ts_ms / (N_minutes×60000)) × (N_minutes×60000)` — NOT session/RTH-open-anchored.** §3's original suggestion ("aligned to session/RTH open") was WRONG and is corrected below. Confirmed three independent ways:

1. **ETL source code** (`src/data/scripts/refresh_local_cache.py:147-209`, `resample_1m_to_tf`): the intraday branch (line 196-209) calls plain `df_1m.group_by_dynamic("ts_event", every=every)` with no `origin`/`offset`/`start_by` argument — pure epoch-anchored default. The function's own docstring confirms daily bars were deliberately special-cased to Globex-session anchoring (deep-scan #10 FIX 3, 2026-07-02) specifically *because* the UTC-midnight default was wrong for daily PDH/PDL — and intraday was **explicitly left on the old path** ("Intraday: existing group_by_dynamic (unchanged)"). `src/data/scripts/resample_timeframes.py:30-43` (the bulk/backfill twin) has the identical unmodified call.
2. **`load_ohlcv` does no resampling** (`src/engine/data_loader.py:868-1009`) — a plain DuckDB `read_parquet` + date-range WHERE + ORDER BY. Bar boundaries are fixed entirely at ETL time, never reconstructed at read time — confirming whatever the ETL wrote is exactly what the backtest evaluates against.
3. **Empirical proof, both local cache and a live read-only S3 query against the real production bucket** (this repo's own `.env` AWS credentials, SELECT-only): ES 4-hour consolidated bars land at UTC **00:00 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00** — pure epoch-truncation boundaries. (5m/15m/1h alone are ambiguous — 18:00 ET happens to coincide with a UTC-hour boundary for any divisor of 60 — but 4h disambiguates conclusively: a Globex-session anchor would land 4h buckets at UTC 22/02/06/10/14/18, not the observed 00/04/08/12/16/20.) Live S3 read of `consolidated/4hour.parquet` reproduced the identical boundaries byte-for-byte against the local cache — not a stale-fixture artifact.

**Design consequence for M1c:** the new live aggregator must bucket on the SAME plain epoch-ms truncation, NOT on `toGlobexSessionDateString`/session-boundary helpers as §3 originally suggested — using the session-boundary helpers would have shipped a fix that still silently diverges from backtest, just less obviously than today's 1-minute bug (per advisor's explicit warning: "swap an obvious wrongness for a subtle one"). Daily is the one confirmed exception (18:00 ET Globex-anchored per FIX 3) but is moot for M1c — zero of the 120 strategies use a daily timeframe. The acceptance gate (§5) must include a parity test against REAL parquet bar timestamps (not just internal unit tests) to prove the aggregator's bucket boundaries match production data, not merely an assumption.

## 0. How this was found (traceability — verify before trusting)

A bar-flow trace (2026-07-17, read-only Explore investigation) was dispatched to answer: does live PAPER-state signal evaluation aggregate raw Massive 1-minute bars into a strategy's configured timeframe (5m/15m/etc.) before evaluating indicators, matching what the backtester does? Findings, independently spot-checked against the live tree by the parent session:

- **Live side — no aggregation exists.** `src/server/routes/paper.ts:201` calls `startStream(session.id, symbols)` — no timeframe argument at all. `paper-trading-stream.ts`'s `ensureSocket()`/`startStream()` create a raw per-symbol WS subscription to Massive's 1-minute `AM` aggregates only (confirmed: M1a's own adapter doc explicitly states "no second-aggregate (A.) bar-builder" by design). `barBuffer` (`paper-trading-stream.ts:56,122,169-192`) is a rolling window of up to 200 **raw 1-minute** bars, passed straight to `evaluateSignals()` (`paper-trading-stream.ts:380`) → `computeIndicators(barBuffer)` (`paper-signal-service.ts:1251,2296,6516`) — no timeframe parameter anywhere in this call chain. The ONLY place `session.timeframe` is consulted in the live signal path is `getBarDurationMs()` (`paper-signal-service.ts:1929-1943`), consumed solely by `setCooldown()` (`:1945-1948`) for a post-trade cooldown window — not for resampling bars or gating indicator computation.
- **Backtest side — genuinely timeframe-native.** `src/engine/backtester.py:3652-3654` (and the DSL entry point, `:6656,6681-6682`) call `load_ohlcv(config.symbol, config.timeframe, ...)`, which (`src/engine/data_loader.py:868-883`) reads from a pre-partitioned, timeframe-native Parquet source (`s3://{bucket}/futures/{symbol}/consolidated/{timeframe}.parquet`) — one file per symbol/timeframe, not resampled at request time from 1-minute data.
- **Live incidence check (DB query run against production DB, 2026-07-17):** of 120 total strategies, 117 are CANDIDATE and 3 NEEDS_ARCHETYPE — **zero strategies are currently in TESTING/SHADOW/PAPER or beyond.** So the bug is producing zero corrupted evidence *today* — nothing has been promoted far enough to be affected yet. However, of the 120 strategies' configured timeframes: `5m: 78, 15m: 15, 4h: 9, 1m: 9, 1h: 6, 30m: 3` — **111 of 120 (92.5%) are non-1m.** The instant any of these strategies is promoted into PAPER and the Massive paid feed begins qualifying days, this bug fires for the overwhelming majority of the pipeline.

## 1. What & why

A strategy configured with `timeframe: "5m"` (or 15m/30m/1h/4h) is, in live paper trading, evaluated on **every raw 1-minute bar** — its indicators (EMA/ATR/etc. lookback windows, cooldown-in-bars, `max_hold_bars`, any bar-counted state) are computed over 1-minute increments regardless of what the strategy's config declares. The backtest that validated this strategy's edge, by contrast, loaded genuinely-aggregated N-minute OHLC bars. This is not a cosmetic mismatch — it is a **unit-of-time divergence**: an `EMA(21)` intended as 21×5-minute bars (105 minutes of lookback) becomes, live, 21×1-minute bars (21 minutes of lookback) — a >4x distortion — plus completely different intrabar signal timing (a live "5m" strategy fires 5x more often than intended, on every 1-minute close instead of every 5-minute close) and incompatible bar-counted cooldown/hold-time semantics.

**Why this matters for the campaign specifically:** the entire point of this campaign is to make PAPER's evidence TRUE before the operator pays for the Massive feed and starts a 5-10-day qualifying window (D5/D6/D7). If this bug ships unfixed, ~92.5% of the strategy pool would generate PAPER evidence that does not reflect what was backtested — a strategy could "qualify" on a completely different (and untested) 1-minute-reactive variant of itself, or a good strategy could be spuriously killed by noise its real (aggregated) timeframe would have filtered out. This is exactly the class of silent producer→consumer divergence the campaign's Wiring-Verification Protocol exists to catch.

## 3. Proposed fix design (for the future M1c implementation wave — NOT built by this packet)

Add a client-side bar aggregator between the raw Massive 1-minute stream and `evaluateSignals()`:
- New pure module, e.g. `src/server/lib/timeframe-bar-aggregator.ts`: given a stream of 1-minute bars and a target timeframe string (`"5m"`/`"15m"`/`"30m"`/`"1h"`/`"4h"`), buckets incoming 1-minute bars into **plain UTC-epoch-truncated windows** — `bucketStart = floor(ts_ms / (N_minutes×60000)) × (N_minutes×60000)` — matching the backtest's `group_by_dynamic` default anchor (§0b; NOT session/RTH-open-anchored — that was this section's original, now-corrected, suggestion), and emits a completed N-minute OHLC bar (open = first bucket's open, high/low = bucket max/min, close = last bucket's close, volume = sum) only once the bucket's window has fully closed — never emits a partial/in-progress bar to the strategy evaluator.
- Wire into `paper-trading-stream.ts`: `ensureSocket()`/`handleBar()` gains an aggregation step per-session (keyed by `session.timeframe`, so two sessions on the same symbol but different timeframes each get correctly independent aggregation) between raw-bar receipt and `evaluateSignals()` invocation. 1m-timeframe strategies pass through unaggregated (byte-identical to today — regression-safety anchor).
- `computeIndicators`/`getBarDurationMs`/cooldown logic: audit for any remaining raw-1m-bar assumption once bars are properly pre-aggregated upstream (should mostly "just work" once fed correctly-bucketed bars, but must be verified, not assumed).
- Parity test: same historical 1-minute tape, run through (a) the new live aggregator + `evaluateSignals`, and (b) the backtester's `load_ohlcv` timeframe-native bars for the same symbol/timeframe/date range → indicator values and signal-firing bars must match (or a documented, bounded tolerance for boundary-timing effects — RED-proof: revert the aggregator, same test must fail).
- Explicitly OUT of scope for M1c (do not build): a server-side/Massive-API-level second-aggregate reconciler (the campaign's existing "Explicitly OUT of scope" section already rejects this — "candle strategies need minute bars; complexity serves fill realism Starter can't certify" — this fix is a LOCAL client-side resampler of already-received 1-minute bars, not a request for Massive to pre-bucket on its end, so it does not conflict with that prior decision).

## 5. Verification plan (for the future M1c wave)

(a) Unit tests on the pure aggregator: epoch-truncation boundary alignment (verified against §0b's empirical evidence, e.g. a 4h bucket must start exactly on UTC 00/04/08/12/16/20), partial-bucket-never-emitted, volume-sum correctness, multi-session-same-symbol-different-timeframe independence. (b) **REAL-DATA parity acceptance gate (not optional, not just internal unit tests):** same 1-minute tape → live aggregator → `evaluateSignals`/`computeIndicators`, vs. the backtest's actual `load_ohlcv` bars for the same symbol/timeframe/window (real consolidated parquet, e.g. via a local cache fixture or a scoped S3 read) → indicator values and signal-firing bars must match within a stated tolerance. RED-proof: revert the aggregator → this exact test must fail (not a generic aggregator-absent test — the test must fail SPECIFICALLY because boundaries diverge, proving it actually exercises anchor correctness, not just presence/absence). (c) 1m-passthrough regression test (byte-identical to pre-fix; the 9 1m strategies are the regression anchor). (d) Downstream bar-counted logic re-check (§0b/advisor flag, not previously in this packet): once bars are genuinely N-minute, verify `getBarDurationMs()`/`setCooldown()`/any `max_hold_bars` consumer composes correctly with the new cadence instead of silently assuming 1-minute bars (e.g. a cooldown expressed in "bars" must not double-count now that each bar covers N real minutes). (e) tsc + touched vitest + relevant pytest + 3 CI gates + system-map:sync. (f) Independent doer≠grader accuracy-validator grade — specifically checking the boundary-alignment edge cases (DST transitions, weekend/holiday gaps interacting with bucket boundaries, and that the real-data parity test in (b) is non-vacuous) since this is exactly the kind of off-by-one class that produces silent, hard-to-notice drift.

## 6. Rollback (for the future M1c wave)
