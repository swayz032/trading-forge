# Wave 26 Cohort Expansion Decision Rules

> Operator reference for go/no-go decisions on adaptive-exit cohort expansion.
> Daily audit reports generated by `scripts/wave26-cohort-audit-report.ts` surface
> the signal data; this document defines what the signals mean.

---

## Context

Wave 25.5 wired adaptive exits LIVE on 2026-05-24. The recommended rollout:

1. **Silver_bullet** on adaptive exits first (1 strategy, 7-14 day cohort)
2. Only after silver_bullet proves clean → expand to a second CANDIDATE (crt or power_of_3)
3. After 30 days of clean operation across 2 strategies → graduated/deployed strategies eligible

**Operator approves every cohort expansion manually.** No batch scripts, no auto-flip.

---

## After 7 days of silver_bullet on adaptive exits

### GO — expand cohort to a second CANDIDATE (crt OR power_of_3) IF:

All of the following must be true:

- `exit_plan_fallback_static` count < 5 per 24h
  _(high fallback count = engine error cluster = investigate before expanding)_

- TP1 source distribution: `liquidity` >= 50% of TP1 fills
  _(engine is finding real intraday DOL targets, not falling back to R-multiple spam)_

- Regime distribution: >= 3 distinct regimes hit across the 7-day window
  _(not stuck on one regime = engine is reading market state correctly)_

- `15:55 ET flatten` event count == days since opt-in
  _(hard invariant proof — if count is low, the flatten path has a gap)_

- Zero `95% DLL force-close` events in the 7-day window
  _(hard safety — any force-close = the strategy had a sizing or stop failure)_

- avg-R per winning trade >= static_styleC baseline
  _(run A/B harness: `npx tsx scripts/wave26-cohort-audit-report.ts --days 7 --strategy silver_bullet`)_

### NO-GO — revert silver_bullet to static_styleC IF:

Any of the following:

- ANY above GO check fails
- Any unexplained Discord CRITICAL alert during the 7-day window
- `exit_plan_fallback_static` count spikes (>= 5 in a single day) — investigate root cause first

---

## After 14 days — broader cohort

(Same 7-day checks above) AND:

- Sharpe ratio of silver_bullet adaptive >= Sharpe ratio of equivalent static baseline
  _(run `python scripts/wave25_exit_engine_ab_report.py --strategy silver_bullet --days 14`)_

- Max drawdown of silver_bullet adaptive <= Max drawdown of static baseline

Expand to second CANDIDATE only after all 14-day checks pass.

---

## After 30 days — graduated/deployed strategies

(Same checks above for each strategy in cohort) AND:

- At least 2 CANDIDATE strategies running adaptive exits cleanly for 30 days

- Operator manually approves each `graduated → adaptive` flip via:
  ```bash
  npx tsx scripts/wave25-pass7-adaptive-opt-in.ts --apply --strategy <name>
  ```
  Dry-run (no `--apply`) first; confirm the diff is correct.

## Reading the daily audit report

The cron fires daily at 17:00 ET (21:00 UTC) and posts to Discord (INFO channel).
Operator can also run it manually at any time:

```bash
# Last 24h snapshot (default)
npx tsx scripts/wave26-cohort-audit-report.ts --days 1 --strategy silver_bullet

# 7-day window for go/no-go decision
npx tsx scripts/wave26-cohort-audit-report.ts --days 7 --strategy silver_bullet

npx tsx scripts/wave26-cohort-audit-report.ts --days 14 --strategy silver_bullet

npx tsx scripts/wave26-cohort-audit-report.ts --days 30
```

## Hard invariants — what to do if they're near-zero

| Invariant | Expected value | Troubleshooting |
|---|---|---|
| `15:55 ET flatten events` | == trading days since opt-in | Check `paper-execution-service.ts` time-stop path; verify `paper.time_stop_flatten` audit fires |
| `BE+1 on TP1 fills` | == TP1 fill count | Check `paper-execution-service.ts:2767` BE+1 logic; verify `paper.tp1_fill` audit fires |
| `67% DLL halts` | Rare but non-zero on volatile days | Normal — monitor trend |
| `95% DLL force-closes` | Zero | Any event = immediate investigation. Check sizing + stop distance |

## Fallback cluster diagnosis

If `exit_plan_fallback_static >= 5 in 24h`:

1. Check reason codes in the daily report — `compute_throw` vs `missing_liquidity` vs other
2. `compute_throw` → `adaptive-exit-engine.ts` threw an exception; check app logs
3. `missing_liquidity` → `liquidity_levels` table is empty for the session; check `liquidity-map-refresh` cron
4. Other reasons → inspect raw audit rows via:
   ```sql
   SELECT result, created_at FROM audit_log
   WHERE action = 'signal.exit_plan_fallback_static'
     AND created_at >= NOW() - INTERVAL '24 hours'
   ORDER BY created_at DESC LIMIT 20;
   ```

## §10b Reconstruction

Every audit event queried by this report is a permanent, append-only record in `audit_log`.
The 90-day reconstruction mandate (CLAUDE.md §10b) means any trade from the last 90 days
can be fully reconstructed from audit_log rows. This report IS the reconstruction harness
for adaptive exits — run it with `--days 90` for a full post-hoc analysis.
